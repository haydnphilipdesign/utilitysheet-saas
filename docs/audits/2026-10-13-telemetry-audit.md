# UtilitySheet telemetry audit — 2026-10-13

UtilitySheet has a useful foundation for counting retained requests, first submissions, saved-form use and AI outcomes, plus a small operational incident system. It is much less effective at explaining **why a seller stopped**, **whether the packet reached its recipient**, or **which dependency caused a slow or failed interaction**. The biggest improvements are safer collection boundaries, truthful metric definitions and a small amount of correlated journey/error evidence. A new analytics vendor is not needed to do that.

The most urgent findings are capability-bearing rate-limit identifiers recorded by Upstash analytics; no application URL redaction on global browser collectors; address-derived filenames in server logs; auxiliary event writes that can report successful actions as failures; and AI search/acceptance metrics that overstate what is known.

### 1. Product journeys and activation

**Request creation.** Dashboard emits `new_request_started` on both navigation clicks (`app/dashboard/layout-content.tsx`) and new-page mount (`app/dashboard/requests/new/page.tsx:224`), then `new_request_created` on a successful response. `first_request_*` means the onboarding path, not a database-verified first request. Server creation logs actor/configuration/email-presence flags and IP/user agent after creating the request and setting it sent (`app/api/requests/route.ts:233`). Reusable intake records source/form provenance plus canonicalization flags, **submitted and canonical full property addresses**, slug/suffix and IP/user agent (`lib/seller-forms/intake.ts:277`).

Admin Telemetry joins customer-owned, non-demo, nondeleted retained records; its request cohort is creation time and completion is `metered_at`. It exposes creation channel, current packet mode/modules, saved-form inventory/use, provider entry modes, repeated creation across adjacent windows, reminders/return links/edits and test-drive conversion (`lib/neon/queries/admin-telemetry.ts:45`). These are useful descriptive reports with explicit denominators. They do not measure actual invite delivery, form-copy history, section answers or causal reminder effectiveness. Current entries/configuration and deletion can change older results; recent cohorts are immature. Source-form nulls correctly remain unknown.

**Seller completion.** Server GET logs `seller_opened` on each access, and changes draft/sent to in_progress before answers (`app/api/seller/[token]/route.ts:338`). Opens are endpoint access, possibly repeat loads, previews or automation, not verified human activity. GET does not continually refresh `last_activity_at` once already in progress. The wizard saves unfinished answers locally and emits `seller_step_viewed` to Vercel (`components/seller-form/SellerWizard.tsx:631`), with coarse labels, mode and demo/test-drive location. Skips, no-result commitments, help/save-link actions and retry clicks also go there. Effect dependencies/revisits can repeat step events; these events carry no request/session join key. Submission HTTP failures are browser-console messages; only clicking retry emits a diagnostic event. Validation failures, the original failed attempt, terminal 409 outcomes and time waiting are not a complete durable funnel.

DB activity uses `suggestions_fetched` / `suggestions_search`, including result provider names, category/counts and query length, not raw search query (`app/api/seller/[token]/suggestions/route.ts:185`, `app/api/seller/[token]/suggestions/search/route.ts:79`). Those asynchronous writes swallow errors; serverless completion may also leave them missing. Fetching suggestions is a proxy for step reach, not proof a list rendered or an answer was given. Seller Progress selects the latest **any** event and derives “Reached” from fetch categories (`app/(admin)/admin/abandonment/page.tsx:71`, `lib/admin/seller-progress.ts:40`). Reminders/reopens/technical events can replace the last seller event. Its population does not share all Telemetry exclusions (notably deleted requests/customer-role filtering), and its inactivity counts use request activity while detail rows use latest event time. Comparing the two is unsafe without aligning definitions.

Accepted submission atomically stores request/entries/metering and a redacted `seller_submitted` summary in a data-modifying SQL statement (`lib/neon/queries/seller-submission.ts:182`; `lib/telemetry/seller-submission.ts:25`). This gives strong durable success evidence and retry semantics. It is not an auxiliary write to casually detach. IP/user agent remain separate event columns even though the JSON excludes seller identity and answer values. Browser `seller_submitted` is separate, may count a response retry, and includes public demo completion; do not add browser and DB counts together.

**Packet delivery/use.** Packet page emits copy/download/phone/website click actions (`app/packet/[token]/page.tsx:204`). Copy/download click counts express intent, not confirmed clipboard/delivery; advanced generated/downloaded events follow a successful browser PDF fetch and are two descriptions of one action. There is no comparable durable public packet-open/download event or recipient role. No evidence establishes that a buyer/coordinator viewed the packet. Vercel pageviews and referral CTA impressions are aggregate hints, not a completed delivery funnel.

**Activation/acquisition.** Server activation provisions durable account/default state (`lib/activation/ensure-account-activation.ts`), and browser events reflect returned creation flags. Dashboard “first view” is deduplicated in **sessionStorage per account**, so it repeats in a new session (`lib/analytics/activation.ts:51`). Email signup completion precedes verification/sign-in; Google emits signup started but not the same completion call (`app/auth/signup/page.tsx:105`). It is not one uniform verified-signup funnel. Storage calls in activation/attribution are not consistently protected against unavailable storage.

Growth measures dashboard/default readiness, request creation, first live submission, habitual accounts and paid-plan access (`lib/admin/activation-funnel.ts:145`). Its submission CTEs depend on `status='submitted'`, unlike Telemetry's first-submission `metered_at`: reopening a previously submitted request can remove historical activation until it is resubmitted. Legacy timing falls back to last activity. Paid-plan access includes entitlements/Team access, not unique paying subscriptions or revenue.

First-touch UTM/referral values and literal landing pathname are saved in localStorage then posted after auth (`lib/growth/attribution.ts:36`; `app/api/growth/attribution/route.ts`). Bounded text sanitization is not a semantic privacy filter: a UTM landing on `/s/...` or `/packet/...` can preserve a capability token in `landingPath`. Acquisition is local-browser first touch, not cross-device attribution. Referral CTA records both Vercel and DB impression/clicks (`components/packet/transaction-referral-cta.tsx`); DB events have no session id/deduplication beyond one component impression, so reloads and anonymous traffic repeat counts. These are exposure ratios, not linked visitor conversion probabilities.

**UX impact.** `createEventLog` throws on DB failure. Request creation, intake start, seller GET and seller return-link email await it without isolating auxiliary failure. Creation/email can already have happened before a 500; intake fails before setting its resume cookie, increasing retry/duplicate risk. Opening can fail before returning the form. Browser SDK `track()` catches ordinary property/queue errors in the installed version, but the app helper has no explicit containment contract; unguarded storage can still disrupt effects/auth progress. Test these boundaries instead of assuming all telemetry is harmless.

### 2. Errors, logs, performance and dependencies

The application has global Web Analytics and Speed Insights, scattered server/client logs and a selectively structured ops system. No repository integration for centralized browser exception reporting, a custom global error collector, OpenTelemetry instrumentation or uniform HTTP operation timing was found in `app`, `lib`, package dependencies and config. Platform-generated logs/traces may exist outside source; their availability and retention were not inspected.

Current logs mix fixed messages, IDs, exception objects, provider messages and sanitized JSON. They usually lack shared operation/correlation id, route template, deployment revision, duration and stable reason. A 4xx validation/refusal is often a direct response with no corresponding incident; zero console errors therefore does not prove successful seller submissions. Speed Insights can help page speed but cannot explain AI wait, DB write duration, contact enrichment or attachment generation. The two device labels collapse narrow desktop/tablet into “mobile_phone” (`lib/analytics/device.ts`), limiting browser/device diagnosis.

Dependency blind spots include Stack Auth failures/reconciliation, Places/autocomplete, optional location verification, Neon, cache/rate-limit availability and asset/browser launch failures. `lib/address/location-verifier.ts:52` sends the raw address to its configured service and silently returns null on timeout/non-OK/parse failure; that is service processing, not AI telemetry, but needs its own privacy/processor boundary. `lib/cache.ts:31` logs raw errors and returns a miss/false: configured Redis outages do not switch to memory inside those catch blocks. `lib/rate-limit.ts:299` awaits persistent limiter enforcement; missing required configuration returns unavailable, whereas a limiter exception bubbles to route handling. Keep enforcement fail-closed; analytics recording failures inside the SDK are caught and placed on a pending promise, which the wrapper discards.

Operational metadata is allowlisted and bounded, with coarse error names (`lib/ops/events.ts:20`). This is a good pattern to extend. Its catch protects against rejected writes but does not bound slow DB awaits; sampled success is availability evidence, not a success denominator. No generic collector protects existing raw `console.error(error)` paths. SDK/SQL exceptions can contain messages, snippets, URLs or connection context. That is a potential disclosure path, not evidence credentials have leaked.

### 3. AI quality, latency, cost and fallback

Runs contain feature/category/model/prompt/pipeline/source/status/reasons, first terminal call-failure kind, pipeline latency, pass count, result count, cache state, coarse locality, token/search/source counts and relational IDs. Items contain provider labels/rank/confidence/canonical id/contact-presence and submission selection correlation. Contact runs intentionally omit provider/contact values. Fresh support/evaluation APIs bypass seller telemetry. Privacy design of the tables broadly matches `docs/ai-telemetry.md`: no raw prompts/responses, streets, seller contacts, meters or submission payloads are intentionally inserted by these telemetry writers.

Useful questions include recorded fallback by category/model/prompt, token use where reported, recorded failure kind, final manual/search mix and whether seller-confirmed names match a generated item. They cannot establish provider/contact accuracy, billable total cost or actual browser impressions.

Specific limits:

- `createAiSuggestionRun` writes the run and items separately (`lib/neon/queries/ai-telemetry.ts:96`, `:178`); an item-write failure leaves a counted run with missing items. Production catches in suggestion/contact callers suppress even a warning, so missing collection can look like low usage.
- Writers are caught **and awaited** before returning suggestions/contact. DB delay still adds to the interaction. Pipeline `latency_ms` is captured before telemetry/cache persistence; cached rows hardcode zero rather than measure a cache/API interaction. UI only exposes average fresh latency, not p95/end-to-end time.
- In-flight deduplication returns the first caller's promise/context (`lib/providers/suggestion-service.ts:1485`). Simultaneous requests for the same scoped key can share generation but only the first request gets a run/item linkage. These are generation records, not one impression per consumer.
- Cache rows use `source='cache'`, null reasons/failure kind and zero attempts. They erase original result provenance, including cached generic/no-list fallback. The model/config and prompt stamped on a cache read are current; no immutable producing-run reference exists. Fresh health does not capture bad cached experiences.
- Selection matches the latest normalized provider name for request/category, not an item id acknowledged by the browser (`lib/neon/queries/ai-telemetry.ts:222`). It can select a later run or search result; repeated exposure inflates item-based “acceptance” denominators. Admin acceptance instead uses the **first generated suggestion run**, current final entries, excludes unknown/not-applicable and omits searches as exposure groups (`lib/neon/queries/admin-telemetry.ts:207`). Neither is calibrated accuracy. Later dashboard edits replace entries and do not preserve equivalent AI selection provenance.
- `attempt_count` is pipeline passes, excluding internal transport retries (`lib/ai/gemini-client.ts:345`). UI “Timeouts”/“Other failed calls” count runs with the first recorded error kind, not every failed call. Transient failed attempts before a successful retry are not completely counted.
- `lib/ai/gemini-client.ts:587` converts missing grounding query arrays to **zero**. The October 12 plan documents historical measurements where JSON-schema calls hid grounding metadata; no current code/UI/doc warning resolves that finding. Zero means zero *reported* queries, not zero real searches. `source_count` is summed per pass, so it is not distinct sources across the complete run. `scripts/eval/eval-core.ts:529` uses those counts for search-cost and cost-per-top3 estimates, which can also understate costs. No production invoice reconciliation or price/versioned cost ledger exists. Failed/timed-out/unrecorded calls and evaluation calls are not a complete billable total.
- Confidence is model/heuristic confidence, not calibrated ground truth. Wrong plausible output can be success; contact miss is success with `ai_empty`; disabling unverified contacts returns without recording a run (`lib/providers/contact-service.ts:280`). Missing contact rows do not distinguish feature disabled from never used.
- AI health checks fresh runs over 24h, defaults 10 minimum/50% degraded; suggestions use fallback source, search/contact use error/parse status (`lib/ops/ai-health.ts:62`). It excludes latency, plausible wrong answers, partial failures that recover and cache outcomes. At low traffic detection can take many hours. A quiet or failed collection stream does not establish health.

AI logs are less private than AI rows: successful contact lookup logs `providerNameOrId` unconditionally (`lib/providers/contact-service.ts:294`), possibly seller-supplied free text; Gemini error metadata carries raw provider messages and JSON parse errors can include output fragments (`lib/ai/gemini-client.ts:234`, `:570`). Suggestions' optional log removes city in the outcome but a separate enabled message includes locality lines (`lib/providers/suggestion-service.ts:1495`). Avoid a blanket claim that AI telemetry privacy rules protect all logging.

### 4. Billing, email, PDF and jobs

**Billing.** Verified webhook processing failures store Stripe event id/type and safe error name; redelivery increments attempts instead of duplicate incident rows, and same-event success records recovery (`app/api/billing/webhook/route.ts:410`; `lib/ops/events.ts:94`). Teams seat mismatch/duplicate subscriptions also create incidents. This helps diagnose known processing failures. It is not a ledger of all handled event types, provider lag, checkout abandonment, missing webhooks or confirmed paid revenue. Routine successes are sampled, even with provider IDs, except recovery. Raw webhook errors/signature failure messages are still logged. A billing write failure should return 500 so Stripe can retry; operational telemetry failure is caught but awaited. Do not weaken signature/idempotency/entitlement handling to improve observability.

**Email.** Reminders have durable intent, shared cooldown/idempotency and accepted/failed/unknown states; provider message ids permit signed delivery-event correlation (`lib/neon/queries/reminder-operations.ts`, `app/api/webhooks/resend/route.ts`). Delivered/bounce/complaint/failure are ordered facts, redelivery-deduplicated; unknown message ids store nothing (`lib/ops/email-delivery.ts:38`). Delivery is not reading. Write failure in a verified delivery webhook deliberately returns 503 for provider retry; the reminder ledger/audit must remain durable.

Completion notifications record grouped failure and sampled success after sending (`app/api/seller/[token]/route.ts:888`). An attachment can fail while email succeeds: the ordinary completion failure filter checks email success only, so this can produce a sampled success with the attachment failure visible only in helper logs. Test-drive events separately summarize attachment success. Each eligible recipient independently builds/sends through the helper, adding latency/work for multi-recipient notifications. `sendTCCompletionNotificationEmail` logs but **does not return/persist** the accepted provider message id (`lib/email/email-service.ts:1189`), so later delivery callbacks are unmatched. Missing eligible recipients are mostly a warning; skips need explicit outcome labels. New-request invitations, seller self-links, team invitations, referral/weekly/activation messages have uneven evidence: console outcomes, activation outreach or test-drive-specific events, but no shared delivery mapping. The create-request caller ignores a returned false email result. Packet readiness must not be confused with notification delivered.

**PDF.** Production download and completion attachments share `lib/pdf/packet-attachment.ts` and the current HTML builder, which returns `print_pdf` (`lib/pdf/packet-html.ts:708`). Logs include launch strategy/renderer; public download failures and sampled success feed ops. Invalid/not-submitted/locked/rate-limited requests are deliberately outside renderer incidents. No durable render-stage timing, output size/page-count metric, per-attempt request correlation or success denominator exists. Public failures deliberately omit packet tokens but also omit request id even after resolution; email attachment failures are grouped under email. Renderer label chooses “advanced_renderer” for print_pdf, which now includes Simple—misleading if used to split mode. A legacy screenshot/readability logging branch remains in the renderer but is not reached by the current builder; do not count it as live monitoring.

**Jobs and alerting.** `vercel.json` schedules three daily jobs plus the 15-minute ops monitor. Start/finish catches store run status, wall duration and numeric counts (`lib/ops/events.ts:217`). Operations only reads `SCHEDULED_JOBS`, excluding `ops_monitor` itself. Weekly-summary has a route and console/count responses, no configured schedule/job-ledger coverage; an external schedule is unverified. Never-observed daily jobs remain “not observed” indefinitely; recently stuck running jobs can look OK based on the preceding success until overdue (`lib/ops/overview.ts:162`). Partial outcomes display but do not fire the “failed” condition. `OPS_ALERT_JOB_OVERDUE_HOURS` is parsed but classification uses the fixed 26h rule; the override does not change the effective overdue decision.

Alerts use the same DB and Resend as the application (`lib/ops/alerts.ts:246`), so DB failure or an email outage can hide its own incident. Alert transitions persist only after accepted send; recording failure afterward can repeat notification next run. AI health read failure becomes null, then the route supplies an empty list; monitor can finish success without AI coverage (`app/api/cron/ops-monitor/route.ts:33`). There is no monitor-of-monitor health in Admin. The health endpoint probes DB only; AI/rate-limit flags are configuration checks. An independent probe is needed for total outage detection. Existence of such a probe is not established.

## Privacy, retention and documentation accuracy

1. **Verified capability-token storage path:** seller/PDF routes pass raw tokens or token+IP to limiters (`app/api/seller/[token]/route.ts:474`, suggestions `:122`, packet PDF `:17`, send-link `:19`). Installed Upstash SDK `dist/index.mjs` records that identifier/time/success through core analytics when enabled (90-day SDK retention setting), as well as using it in Redis counter keys. Wrapper discards `pending`, so not every analytics write is guaranteed to complete. Turning analytics off alone would not remove raw tokens from counter keys. This is conditional on configured Redis; historical provider contents were not read.
2. **Browser URL risk:** Analytics and Speed Insights are global with no `beforeSend` or sensitive-route filtering. A dynamic route label is not proof full URLs/queries are removed. Tokens, intake slugs, auth/invite parameters and account identifiers can appear in URL telemetry. Actual beacons were not captured. Supported filter/redaction hooks exist in installed SDKs and [Vercel Analytics guidance](https://vercel.com/docs/analytics/redacting-sensitive-data), [Speed Insights configuration](https://vercel.com/docs/speed-insights/package). Verify using intercepted synthetic beacons, without sending real traffic.
3. **Verified address copies:** intake event JSON duplicates full addresses; attribution can retain a capability-bearing pathname; email attachment success logs include filenames built from street address (`lib/pdf/packet-html.ts:690`, `lib/email/email-service.ts:1147`). Dormant readability code also logs filename; do not call that branch an observed leak. Demo redirect logs a destination email if enabled. Retain full identity data in operational business records where needed, not auxiliary logs.
4. **Raw log risks:** SQL/provider exceptions, Gemini messages/output parse snippets and provider-name free text lack a shared redaction boundary. No secret value was read/exposed in this report. Safe ops metadata does not protect every raw log or its unconstrained provider/correlation id fields; those are caller contracts.
5. **Retention/deletion:** only operational events/job runs have configurable 90-day pruning, disabled until enabled. No analogous scheduled AI/item/event-log retention was found. `schema.sql:271`/`:309` uses SET NULL on AI request links, so deleting a request can leave locality/provider/final-selection rows; event logs cascade on hard deletion, not soft deletion. Account closure tombstones/transfers/deletes selected records (`lib/neon/queries/account-closure.ts:483`), not a blanket purge of all telemetry/provider stores. Local drafts contain answers by design; do not attach them to error reports. Decide retention/access/deletion coverage before exporting or adding collectors.

Documentation is broadly accurate about AI table redaction and best-effort rejection handling, metering-based Telemetry cohorts and reminder delivery limits. It needs these explicit corrections: “shown” is generated/served without browser acknowledgment; one-run/contact claims have disabled/in-flight exceptions; “never block” does not imply bounded latency; search/source counts are metadata estimates, not billed counts; source totals are per pass; failed-call UI counts are run counts. The operations runbook still contains old “no commit”, “no vercel.json change” and pre-monitor schedule text alongside later completion notes. Preserve the history in plans, but update current operating instructions during implementation. No production feature/flag state should be inferred from those stale checkboxes.
