**Files:** `lib/rate-limit.ts` or a small shared server identifier helper; seller submission/suggestion/search/send-link and packet PDF limiter call sites; `app/layout.tsx` with a client collector wrapper; `lib/analytics/events.ts`; `lib/growth/attribution.ts`; `app/api/growth/attribution/route.ts`; focused tests and tracked telemetry/privacy docs. **Implementation:**

1. Define a deterministic namespaced SHA-256 digest of high-entropy capability-bearing identifiers before calling the limiter, so neither counter keys nor its analytics see the raw token. Preserve current logical grouping: per-token submission, per-token+IP AI/PDF, per-token self-link. Do not log hash inputs, and do not silently convert other policies to new buckets. Hashing a token-containing identifier is appropriate because the token has high entropy; plain hashing IP/email alone is not equivalent privacy protection.
2. Treat key migration as a security change: old and new buckets differ, temporarily resetting counts. Document longest affected policy window and a release strategy that preserves enforcement (e.g. temporary checking of both legacy/new counters over that window, or explicitly reviewed rollout timing). The local patch must not assume permission to clear Redis keys or deploy. Disabling analytics alone is insufficient because raw counter keys remain.
3. Use installed `beforeSend` hooks for both collectors; canonicalize sensitive seller/packet/intake/invite/auth/admin paths to approved static route labels and remove query/fragment values, or drop events if safely normalizing the installed SDK payload is uncertain. Normalize both URL and route where supported. Validate all collector fields, not just dashboard route labels. Preserve coarse seller custom events where the SDK supports safe URL replacement; otherwise document lost measurements until first-party diagnostics exist.
4. Apply the same route policy to first-touch landingPath on client and server. Allowlisted campaign/referral attribution can remain, but do not treat arbitrary UTM text as automatically safe. Remove optional raw `token` from custom-event types; search actual callers before removing unused declarations.

**Tradeoffs:** stable digests remain linkable and are not anonymous; URL scrubbing reduces path-specific diagnostics; a bucket migration requires a careful release window. No new secret/vendor is required for high-entropy token hashing. IP-only pseudonymization is separately scoped.

**Release UX readiness (reviewed 2026-10-13):** traffic gating and maintenance-specific UI are not built. Existing seller submission retains answers/retry and best-effort local drafts on generic failures, but provider search can show unavailable responses as empty results and PDF errors are generic. Before an actual paused cutover, separately prepare/test clear maintenance messages for new visits and existing tabs, honest draft/resume guidance, temporary 503/Retry-After responses and recovery. This release preparation does not reopen completed local Slice 1; tentative evening timing has not scheduled or authorized production changes.

**Acceptance/validation:** synthetic tokens, query credentials, addresses and account ids absent from captured collector/limiter/attribution payloads; same logical identifier yields same bucket, distinct identifiers remain distinct, thresholds/fail-closed semantics unchanged. Add unit fixtures for encoded paths and URL parsing failures; mock both SDK middleware hooks and limiter calls; Playwright intercept synthetic beacons rather than transmit. Run focused Vitest, affected ESLint and `npm exec tsc -- --noEmit`. No live Redis/telemetry calls.
